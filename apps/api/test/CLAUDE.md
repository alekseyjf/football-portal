# E2E API — правила

Підвантажується лише при роботі з `apps/api/test/`. Чому так — [D30](../../../docs/decisions/D30-testing-and-local-env.md), механіка — коментарі в `support/`.

- Тести живуть в окремій схемі `e2e` тієї самої БД, що й розробка; `public` — справжні дані.
- Застосунок — лише `createE2eApp()` (`support/e2e-app.ts`), не вручну з `AppModule`: адаптер Prisma 7 ігнорує `?schema=`, і справжній `PrismaService` писав би в `public`. `{ unavailableDatabaseUrl }` — для тестів «БД недоступна».
- Кожен файл починає з `resetE2eData(e2e.prisma)`; файли йдуть по одному (`maxWorkers: 1`) і не залежать один від одного.
- Схему не чіпати через `prisma migrate` / `db push` — її перебудовує `globalSetup` з `prisma/migrations` на кожен прогін.
- Користувачі — `createUser` / `loginAs` (`support/e2e-auth.ts`): ≤ 5 реєстрацій на файл (ліміт з IP). Ключа football-data немає — синк відповідає 503.
- Підключення — `E2E_DATABASE_URL` або `DIRECT_URL` (session pooler); transaction pooler не підходить (`search_path`). CI (job `e2e-api`, `.github/workflows/ci.yml`) — сервіс `postgres:17` (як Supabase) і `E2E_DATABASE_URL`, пояс раннера — UTC: тест не має залежати від поясу процесу (перевірка — `TZ=UTC pnpm test:e2e`).
- Файли — `test/<модуль>/*.e2e-spec.ts`; запуск модуля з кореня — `pnpm test:e2e -- test/<модуль>/`: шаблон шукає в повному шляху, і `-- football` запустить усі файли (шлях репозиторію — `…/football-portal/…`).
- Контракт ([D28](../../../docs/decisions/D28-openapi-contract.md)): відповідь ендпоінта — `expectMatchesContract(response, 'get', '/posts/{number}')` (`support/openapi-contract.ts`): статус описаний у `packages/types/openapi.json`, тіло — за схемою, без незадокументованих полів. Змінив DTO чи роут — спершу `pnpm gen:api-types`.
- Покриття контракту: повний прогін (без шаблону) падає в `globalTeardown`, якщо в операції `openapi.json` немає жодної 2xx-відповіді, перевіреної `expectMatchesContract` (`support/contract-coverage.ts`). Новий ендпоінт — з e2e успіху; 2xx, яку e2e не відтворити, — у `OPERATIONS_WITHOUT_SUCCESS_E2E` з причиною.
- Cron-и тест-застосунку зупинено (`createE2eApp`): воркер розкладу (раз на хвилину, D57) опублікував би заплановані посеред тесту — прохід кличе тест (`app.get(ScheduledPostPublisher).publishDue(now)`); стенду, якому cron потрібен, — `SchedulerRegistry.getCronJobs()` → `start()`. Події — `app.get(EventEmitter2).on(…)`; вебхук web — локальний `http.createServer` + `envOverrides` (`site-revalidation/`).
- Env тест-застосунку — `createE2eApp({ envOverrides })` (`COMMENT_COOLDOWN_MS: '0'`, прод-режим); турнір з матчами й таблицею — `seedFootballLeague` (`support/e2e-football.ts`): синк без ключа не працює; сезон з учасниками й матчами заданих статусів (турнір «у грі» чи ні, D48) — `createFootballSeason`.
- supertest: `request(server)` слухає порт лише до кінця свого запиту — запит створювати там, де його `await`-ять, а не масивом наперед (інакше `ECONNREFUSED`).
- Відомий флейк (2026-10-24, M1.6.1): прогін раз упав з кодом 139 (segfault процесу Jest) одразу після перебудови схеми, ще до тестів; три наступні повні прогони — зелені. M1.6.2 (того ж дня): ще раз — код 1 без жодного рядка Jest одразу після перебудови схеми; і окремо раз упав один тест у `posts/post-url` (виведення не збережено) — повтори зелені. Повний прогін — з логом у файл (`pnpm test:e2e > e2e.log 2>&1`), щоб наступного разу була причина. Повторилось — перезапустити; двічі поспіль — `--logHeapUsage` і запуск файлів по одному, щоб знайти файл і пам'ять. `maxWorkers: 1` не міняти: файли ділять одну схему `e2e`, паралельний прогін зламає їхні дані.
- Гонка — детерміновано: блокування тримає окрема транзакція (`e2e.prisma.$transaction`), тест чекає, доки запит застрягне на ньому (`pg_stat_activity`, `wait_event_type = 'Lock'`), і лише тоді відпускає (`finally`); CHECK з `constraints.sql` — записом в обхід API. Приклад — `tags/tags.e2e-spec.ts`.

## БД розробки (Supabase) і разові скрипти
- `tenant/user postgres.<ref> not found` — безкоштовний проєкт Supabase призупинено за неактивність: відновлює власник у дашборді, рядок підключення не винен. Transaction pooler (:6543) іноді «висне» на мертвому з'єднанні до ~15 хв — довгі прогони й скрипти — через `DIRECT_URL` (:5432); завис запит — спершу перевірити `SELECT 1`, потім код.
- `.env` читає лише власник: значення не друкувати й не копіювати; потрібна зміна — точні рядки власнику.
- Разовий скрипт на `pg` (node-postgres): до міграції 0010 дати були `timestamp` без поясу, і `pg` читав їх як місцевий час (на Mac у Києві — мінус 3 год); з 0010 — `timestamptz`, читаються правильно. Порівнювати дати між середовищами — `::text` з поясом або через Prisma.
- Репетиція міграції на справжніх даних dev-БД, `public` не змінюючи: одна транзакція — `CREATE TEMP TABLE "X" (LIKE public."X" INCLUDING ALL)` + копія рядків, `SET LOCAL search_path TO pg_temp, public` (і перевірити `current_schema()`), міграція й SQL відкату на копіях, відбитки колонок до й після (кількість, NULL-и, md5 відсортованих значень), `ROLLBACK`. Так перевірено 0010 (M1.6.4).
- Prisma-скрипт поза застосунком (сід, стенд, разовий) — лише клієнтом `createSchemaPrismaClient(url, schema)` і `assertSchemaTarget` до першого запису (`prisma/schema-target.ts`; на них же `createE2ePrismaClient` і глобальний setup e2e). Схему таблиць адаптер Prisma 7 бере лише з параметра `PrismaPg(…, { schema })`, а `search_path` / `?schema=` з рядка підключення для них ігнорує: M1.8.3a — сід з `search_path=e2e` у `DIRECT_URL` пішов у `public` dev-БД (ідемпотентний, нічого не змінив; перевірено кількостями й датами). Сід тепер пише лише туди, куди каже `SEED_TARGET_SCHEMA`.
- Перевірка відновлення дампу й репетиція на копії **всієї** схеми (так перевірено 0011, M1.6.4): `pg_dump --schema=public --no-owner --no-privileges` → `public.` → `restore_check.` лише в DDL і рядках `COPY …` (дані — як є), без `CREATE SCHEMA public` (схему створює репетиція) → в одній транзакції: дамп, `SET client_min_messages TO notice` (дамп ставить `warning` і ховає `NOTICE` перевірок), порівняння рядків і md5 кожної таблиці з `public`, міграція → SQL відкату (двічі — ідемпотентність) → міграція з відбитками даних після кожного кроку, `ROLLBACK`. `setval` нетранзакційний — зачіпає лише послідовності `restore_check`, що зникають разом зі схемою.
- Плани запитів (`EXPLAIN (ANALYZE, BUFFERS)`) — на синтетичних рядках у схемі `e2e` зі справжнього репозиторію зі збірки (`apps/api/dist`, SQL ловить подія `query` Prisma — ручний SQL дає інші плани); `ANALYZE` — лише таблиць `e2e`, гіпотеза індексу — у `BEGIN … ROLLBACK`. Прибирати не треба: наступний `pnpm test:e2e` перебудує схему.

## Жива перевірка в браузері
- Стенд: API зі збірки (`apps/api/dist`, спершу `nest build`) на схемі `e2e` — скрипт у scratchpad повторює `createE2eApp` (`Test.createTestingModule({ imports: [AppModule] })`, свої `envConfig` з випадковими секретами й `CORS_ORIGINS` для :3000 / :3001, `PrismaService` — `createE2ePrismaClient`: схема таблиць — параметр адаптера, не `search_path`), на старті чистить таблиці, вставляє мови й засіває дані через API, слухає :4000; web / admin — `next start` (`next build` спершу; web — з `SITE_URL=http://localhost:3000`, без неї production-сервер не стартує) або `next dev`. Браузер — системний Chrome через `puppeteer-core` у scratchpad (не в репозиторії), профіль — постійний.
- Швидший стенд — з джерел, без `nest build` (M1.8.1): скрипт `.ts` у scratchpad імпортує `test/support/*` за абсолютним шляхом (`createE2eApp({ envOverrides: { CORS_ORIGINS } })`, `resetE2eData`, `seedFootballLeague`, `createUser` / `loginAs` — засів через API), наприкінці `e2e.app.listen(4000)`; запуск — з `apps/api`: `npx ts-node --transpile-only -P tsconfig.json <скрипт>`. Пакети (`@prisma/client`) скрипт бере теж за абсолютним шляхом — з scratchpad вони не резолвляться. Межі полів засіву — як у DTO (анонс ≥ 10, текст ≥ 20 символів).
- Перезапуск стенду — нові секрети й порожні таблиці: старі cookies → 401, вхід заново. Ліміти — у пам'яті процесу: реєстрація 5 / 10 хв з IP, вхід 10 / 15 хв на акаунт, коментарі — пауза 60 с.
- Стенд для Lighthouse (M1.8.4): `seedFootballLeague` пише емблеми й прапор з неіснуючого `e2e.test` — у браузері це помилки завантаження в консолі, а їх рахує аудит Best Practices (`errors-in-console`); після засіву — справжні адреси CDN football-data (`https://crests.football-data.org/PL.png`, клуби — `57.png`, `61.png`, прапор — `770.svg`), обкладинки — з Unsplash / Pexels (перевірити `curl`, що адреса віддає фото). Сайт — `next start` з `SITE_INDEXING=true` (інакше `X-Robots-Tag: noindex` і SEO < 100); холодний кеш фото — видалити й `.next/cache/images`.
- Кеш даних web (`apps/web/.next/cache/fetch-cache`, M1.8.3) переживає перезапуск `next start` і новий засів: новина з тим самим номером показує дані попереднього стенду, бо вебхук без `WEB_REVALIDATE_URL` не приходить (M1.8.3a). Перед новим засівом — зупинити web і видалити теку (або налаштувати вебхук).
- Перед збіркою для заміру — `dist` пакетів і типи API з поточної гілки (M1.9): вони не в git і лишаються від іншої гілки чи скасованої роботи (`COVER_IMAGE_MAX_WIDTH` скасованого M1.9.1 потрапив у збірку web) — `pnpm --filter @football-portal/validation build`, `pnpm gen:api-types`.
- Чим малює браузер (M1.9): CDP `CSS.getPlatformFontsForNode` вузла — назва шрифту й `isCustomFont`; computed `font-family` цього не каже (Geist у класі, а малював Arial: `font-family` на `body` перебивав клас на `<html>`). Розкладка залогіненого без входу — підміна відповіді `GET /auth/me` у `setRequestInterception` (із заголовками CORS); запасний шрифт — `abort()` запитів `.woff2`.
- Текст сторінки — `document.body.innerText`, не `textContent`: той бачить і RSC-дані в `<script>` (статична сторінка адмінки несе там «Loading posts…» запасного вмісту `Suspense`).
- `next start` префетчить кожне видиме посилання на динамічну сторінку; `networkidle` на сторінці з посиланням на 404 не настає — чекати `load` і селектор. Після `load` сторінка ще гідрується: спершу дочекатись елемента, потім клікати.
- Фонові вкладки headless — `document.visibilityState = 'hidden'`: TanStack Query там таймер опитування пропускає (так і задумано), а `click` puppeteer чекає кадру, якого фонова вкладка не малює, — `page.bringToFront()` перед діями; видимість для перевірки опитування — підміна `visibilityState` + подія `visibilitychange`. Перехоплення запитів (`setRequestInterception`) не вимикати посеред роботи сторінки — запити, що встигли потрапити між зняттям обробника й вимкненням, «висять»; краще обробник, що пропускає все.
- Контрольний прогін (зламати → перевірка падає): копія файлу до поломки, відновлення й звірка байт у байт, після нього — чиста збірка. Файли — CRLF: шаблон поломки на кілька рядків — з `\r?\n`, і перед прогоном перевірити, що зміна справді є (`diff`), інакше «зелений» контроль нічого не доводить.
- Поле форми (M1.7.4): ⌘A у headless-Chrome на macOS текст не виділяє — `textarea.select()` / `input.select()` і Backspace, інакше новий текст допишеться до старого. Кожну 4xx-відповідь мережі Chrome пише в консоль («Failed to load resource: … 403»): навмисна відмова API в перевірці (вікно зміни минуло) — не помилка коду; рахувати їх окремо від винятків JS.
- CLS (M1.7.3): `PerformanceObserver` `layout-shift` з `hadRecentInput` — у `evaluateOnNewDocument`. Клік — лише справжній (`ElementHandle.click()`): `el.click()` усередині сторінки для браузера не дія користувача, і зсуви від нього рахуються. Повільне API — затримка потрібних запитів у `setRequestInterception` (інші — `continue()` одразу): зсув, що настає пізніше ніж за 500 мс після кліку, рахується, тож на швидкому стенді його не видно.

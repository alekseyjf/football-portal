# E2E API — правила

Підвантажується лише при роботі з `apps/api/test/`. Чому так — [D30](../../../docs/decisions/D30-testing-and-local-env.md), механіка — коментарі в `support/`.

- Тести живуть в окремій схемі `e2e` тієї самої БД, що й розробка; `public` — справжні дані.
- Застосунок — лише `createE2eApp()` (`support/e2e-app.ts`), не вручну з `AppModule`: адаптер Prisma 7 ігнорує `?schema=`, і справжній `PrismaService` писав би в `public`. `{ unavailableDatabaseUrl }` — для тестів «БД недоступна».
- Кожен файл починає з `resetE2eData(e2e.prisma)`; файли йдуть по одному (`maxWorkers: 1`) і не залежать один від одного.
- Схему не чіпати через `prisma migrate` / `db push` — її перебудовує `globalSetup` з `prisma/migrations` на кожен прогін.
- Користувачі — `createUser` / `loginAs` (`support/e2e-auth.ts`): ≤ 5 реєстрацій на файл (ліміт з IP). Ключа football-data немає — синк відповідає 503.
- Підключення — `E2E_DATABASE_URL` або `DIRECT_URL` (session pooler); transaction pooler не підходить (`search_path`).
- Файли — `test/<модуль>/*.e2e-spec.ts`; запуск модуля з кореня — `pnpm test:e2e -- test/<модуль>/`: шаблон шукає в повному шляху, і `-- football` запустить усі файли (шлях репозиторію — `…/football-portal/…`).
- Контракт ([D28](../../../docs/decisions/D28-openapi-contract.md)): відповідь ендпоінта — `expectMatchesContract(response, 'get', '/posts/{number}')` (`support/openapi-contract.ts`): статус описаний у `packages/types/openapi.json`, тіло — за схемою, без незадокументованих полів. Змінив DTO чи роут — спершу `pnpm gen:api-types`.
- Покриття контракту: повний прогін (без шаблону) падає в `globalTeardown`, якщо в операції `openapi.json` немає жодної 2xx-відповіді, перевіреної `expectMatchesContract` (`support/contract-coverage.ts`). Новий ендпоінт — з e2e успіху; 2xx, яку e2e не відтворити, — у `OPERATIONS_WITHOUT_SUCCESS_E2E` з причиною.
- Env тест-застосунку — `createE2eApp({ envOverrides })` (`COMMENT_COOLDOWN_MS: '0'`, прод-режим); турнір з матчами й таблицею — `seedFootballLeague` (`support/e2e-football.ts`): синк без ключа не працює; сезон з учасниками й матчами заданих статусів (турнір «у грі» чи ні, D48) — `createFootballSeason`.
- supertest: `request(server)` слухає порт лише до кінця свого запиту — запит створювати там, де його `await`-ять, а не масивом наперед (інакше `ECONNREFUSED`).
- Відомий флейк (2026-10-24, M1.6.1): прогін раз упав з кодом 139 (segfault процесу Jest) одразу після перебудови схеми, ще до тестів; три наступні повні прогони — зелені. M1.6.2 (того ж дня): ще раз — код 1 без жодного рядка Jest одразу після перебудови схеми; і окремо раз упав один тест у `posts/post-url` (виведення не збережено) — повтори зелені. Повний прогін — з логом у файл (`pnpm test:e2e > e2e.log 2>&1`), щоб наступного разу була причина. Повторилось — перезапустити; двічі поспіль — `--logHeapUsage` і запуск файлів по одному, щоб знайти файл і пам'ять. `maxWorkers: 1` не міняти: файли ділять одну схему `e2e`, паралельний прогін зламає їхні дані.
- Гонка — детерміновано: блокування тримає окрема транзакція (`e2e.prisma.$transaction`), тест чекає, доки запит застрягне на ньому (`pg_stat_activity`, `wait_event_type = 'Lock'`), і лише тоді відпускає (`finally`); CHECK з `constraints.sql` — записом в обхід API. Приклад — `tags/tags.e2e-spec.ts`.

## БД розробки (Supabase) і разові скрипти
- `tenant/user postgres.<ref> not found` — безкоштовний проєкт Supabase призупинено за неактивність: відновлює власник у дашборді, рядок підключення не винен. Transaction pooler (:6543) іноді «висне» на мертвому з'єднанні до ~15 хв — довгі прогони й скрипти — через `DIRECT_URL` (:5432); завис запит — спершу перевірити `SELECT 1`, потім код.
- `.env` читає лише власник: значення не друкувати й не копіювати; потрібна зміна — точні рядки власнику.
- Разовий скрипт на `pg` (node-postgres): до міграції 0010 дати були `timestamp` без поясу, і `pg` читав їх як місцевий час (на Mac у Києві — мінус 3 год); з 0010 — `timestamptz`, читаються правильно. Порівнювати дати між середовищами — `::text` з поясом або через Prisma.
- Репетиція міграції на справжніх даних dev-БД, `public` не змінюючи: одна транзакція — `CREATE TEMP TABLE "X" (LIKE public."X" INCLUDING ALL)` + копія рядків, `SET LOCAL search_path TO pg_temp, public` (і перевірити `current_schema()`), міграція й SQL відкату на копіях, відбитки колонок до й після (кількість, NULL-и, md5 відсортованих значень), `ROLLBACK`. Так перевірено 0010 (M1.6.4).
- Плани запитів (`EXPLAIN (ANALYZE, BUFFERS)`) — на синтетичних рядках у схемі `e2e` зі справжнього репозиторію зі збірки (`apps/api/dist`, SQL ловить подія `query` Prisma — ручний SQL дає інші плани); `ANALYZE` — лише таблиць `e2e`, гіпотеза індексу — у `BEGIN … ROLLBACK`. Прибирати не треба: наступний `pnpm test:e2e` перебудує схему.

## Жива перевірка в браузері
- Стенд: API зі збірки (`apps/api/dist`, спершу `nest build`) на схемі `e2e` — скрипт у scratchpad повторює `createE2eApp` (`Test.createTestingModule({ imports: [AppModule] })`, свої `envConfig` з випадковими секретами й `CORS_ORIGINS` для :3000 / :3001, `PrismaService` — `PrismaPg` з `search_path=e2e`), на старті чистить таблиці, вставляє мови й засіває дані через API, слухає :4000; web / admin — `next start` (`next build` спершу; web — з `SITE_URL=http://localhost:3000`, без неї production-сервер не стартує) або `next dev`. Браузер — системний Chrome через `puppeteer-core` у scratchpad (не в репозиторії), профіль — постійний.
- Перезапуск стенду — нові секрети й порожні таблиці: старі cookies → 401, вхід заново. Ліміти — у пам'яті процесу: реєстрація 5 / 10 хв з IP, вхід 10 / 15 хв на акаунт, коментарі — пауза 60 с.
- `next start` префетчить кожне видиме посилання на динамічну сторінку; `networkidle` на сторінці з посиланням на 404 не настає — чекати `load` і селектор. Після `load` сторінка ще гідрується: спершу дочекатись елемента, потім клікати.
- Контрольний прогін (зламати → перевірка падає): копія файлу до поломки, відновлення й звірка байт у байт, після нього — чиста збірка.

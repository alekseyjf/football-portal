# ⭐ Правила: чистий код і архітектура

> Загальні принципи, які доповнюють `backend.md` / `frontend.md` / `code-style.md`. Мета — код, який легко читати, змінювати й тестувати. Приклади — з цього проєкту.

## Архітектура

**1. Залежності йдуть у один бік.** Контролер → сервіс → репозиторій → Prisma. Нижній шар не знає про верхній: репозиторій не кидає HTTP-винятки, сервіс не читає `req`, домен football не знає про провайдера (лише `integration/` знає формат football-data).

**2. Межі модулів.** Модуль відкриває назовні лише те, що в `exports` його Nest-модуля; чужі репозиторії напряму не імпортуємо. Залежність між доменами — в один бік (content → football можна, football → content — ні, 🧭 п. 1).

**3. Порт і адаптер для всього зовнішнього.** Зовнішній сервіс (football API, пошта, сховище файлів, платежі) — за інтерфейсом у нашому коді; реалізація — замінний адаптер. Так новий провайдер = новий адаптер, без змін бізнес-логіки.

**4. Бізнес-правила — у чистих функціях.** Рішення без побічних ефектів (переходи статусу, LIVE-вікно, slug, межі дня) — окремі функції з unit-тестами (`resolvePostPublication`, `groupMatchesIntoRounds`). Сервіс лише збирає дані, викликає правило і зберігає результат.

**5. Валідуємо на межі — довіряємо всередині.** Усе зовнішнє (HTTP-тіло, query, env, відповідь провайдера) перевіряємо один раз на вході (DTO, схема env, маппер). Усередині системи — типи, без повторних перевірок «про всяк випадок».

**6. Один сервіс — одна відповідальність.** Сервіс розрісся понад ~300 рядків або обслуговує різні сценарії — ділимо за use case (як `FootballSyncService` / `FootballLiveSyncService` / `FootballSyncWriter`).

## Функції й класи

**7. Функція робить одну річ** і вміщається на екран (орієнтир — до ~40 рядків). Назва каже, що вона робить; якщо в назві «і» — це дві функції.

**8. Ранній вихід замість вкладеності.** Спершу відсікаємо помилки й крайні випадки (`if (!post) throw …`), далі — основний шлях без зайвих рівнів `if`.

**9. Без магічних чисел і рядків.** Числа й коди — іменовані константи поруч із доменом (`COMMENT_COOLDOWN_MS`, `MAX_COMMENT_THREAD_DEPTH`, коди помилок `POST_NOT_FOUND`); спільні межі — у `packages/validation`.

**10. Явні побічні ефекти.** Функція, що пише в БД, шле запит чи змінює стан, — це видно з назви й місця (сервіс / репозиторій). Чисті утиліти нічого не змінюють; аргументи не мутуємо — повертаємо новий об'єкт.

**11. Мало параметрів.** Більше 3 — передаємо об'єкт з іменованими полями.

## Помилки

**12. Очікувані помилки — з кодом, неочікувані — 500 без деталей.** Бізнес-помилка = HTTP-статус + стабільний код (`COMMENT_THREAD_LOCKED`), який розуміє фронт. Внутрішні деталі (SQL, стек, шляхи) клієнту не віддаємо.

**13. Не ковтаємо помилки.** Порожній `catch` заборонено: або обробляємо (повтор, fallback, зрозуміле повідомлення), або логуємо й прокидаємо далі. Помилки Prisma — лише через `prisma-errors.ts`.

## Простота

**14. KISS і YAGNI.** Робимо те, що потрібно зараз, найпростішим способом, що відповідає правилам. Не додаємо «на майбутнє» параметри, абстракції, конфіги без реальної потреби (майбутнє — в `ideas.md`).

**15. DRY з розумом.** Однакова **логіка** — в одному місці. Схожий на вигляд, але різний за змістом код не об'єднуємо: абстракцію робимо, коли випадків три й вони справді однакові.

**16. Без мертвого коду.** Закоментований код, невикористані функції, експорти й залежності — видаляємо (історія є в git). TODO — лише з посиланням на пункт плану / бэклогу.

**17. Правило бойскаута.** Код, якого торкаємось у задачі, лишаємо трохи чистішим — але без великих рефакторингів поза задачею (їх — окремим пунктом плану).

## Frontend (React)

**18. Компонент рендерить, хук думає.** Дані й логіка — у хуках (`useComments`), компонент — розмітка. Компонент > 200 рядків — ділимо.

**19. Стан — мінімальний і поруч з місцем використання.** Похідне значення обчислюємо під час рендеру, а не зберігаємо в стані; серверні дані — лише в TanStack Query, не копіюємо їх у `useState` / Zustand.

**20. `useEffect` — лише для синхронізації із зовнішнім світом** (браузерні API, підписки). Для обчислень і реакції на дії користувача — обробники подій і рендер.

## Тести

**21. Тест перевіряє поведінку, а не реалізацію** — вхід → результат / стан у БД, без перевірки внутрішніх викликів. Назва тесту описує правило («чернетка за номером → 404»). Баг → спершу тест, що його відтворює, потім виправлення.

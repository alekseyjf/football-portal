## Масштабування ([D41](decisions/D41-single-instance-scaling.md))

| Задача | ⏰ Тригер |
|---|---|
| Throttler на Redis (ліміти спільні для інстансів і переживають рестарт) | > 1 інстансу API |
| Анти-абуз на Redis: ковзне вікно порушень (ZSET) замість підрахунку санкцій у БД | > 1 інстансу або навантаження |
| Сховище сесій `sid` у Redis (без запиту до БД на кожен запит) | Навантаження на `JwtStrategy` |
| Окремий worker синку (`NestFactory.createApplicationContext`) + прапорець cron в API | > 1 інстансу API |
| Спільна квота football-data (БД або Redis) | Синк і API — різні процеси |
| Кеш у Redis | > 1 інстансу і виміряна потреба ([D35](decisions/D35-caching-measure-first.md)) |
| Спільний cache handler Next (Redis) для web: кеш `fetch` і `revalidateTag` з вебхука — спільні для інстансів (зараз — пам'ять / диск процесу, M1.8.3) | Перед другим інстансом web — інакше вебхук очистить кеш лише того інстансу, куди потрапив |
| ⭐ Стрічка `GET /posts` на тисячах новин. ⭐ Виміряно в M1.8.2 (`EXPLAIN (ANALYZE, BUFFERS)` параметризованого SQL Prisma, синтетичні 20 000 новин, 86 % живих, схема `e2e`, гіпотези — у `BEGIN … ROLLBACK`): **вибірка** сторінки 1 — 32 мс, `Seq Scan` + `Hash Join` з перекладом + top-N sort (індекс `[status, deletedAt, publishedAt desc]` без `id` порядку стрічки не дає); **`count`** — 21–23 мс, повний прохід за будь-якого індексу. Частковий `("publishedAt" DESC, id DESC) WHERE status = 'PUBLISHED' AND "deletedAt" IS NULL` з SQL Prisma **не працює** (0,19 мс лише зі статусом-літералом): Prisma передає статус як `CAST($1::text AS "PostStatus")`, а перетворення в enum не незмінне — планувальник не доводить умову індексу. Працює **`Post("status", "publishedAt" DESC, "id" DESC) WHERE "deletedAt" IS NULL`** — вибірка 32 → 0,19 мс з параметром Prisma; він же покриває воркер і sitemap (може замінити наявний). `count` — кеш лічильника (кеш стрічки M1.8.3 / [D35](decisions/D35-caching-measure-first.md)). Раніше, в M1.4.7 ([D46](decisions/D46-post-feed-filters.md); синтетичні 20 000 новин, схема `e2e`): сторінка й `total` — до ~65 мс кожен з широким фільтром (турнір на третину новин), ~25 мс без фільтра — бо сортується вся відібрана стрічка. Що допомагає (виміряно там же): частковий індекс у порядку стрічки `Post("publishedAt" DESC, id DESC) WHERE "deletedAt" IS NULL AND status IN ('PUBLISHED', 'SCHEDULED')` — сторінка 1: 22 → 0,15 мс без фільтра, 35 → 0,3 мс з широким фільтром (глибокі сторінки й `total` — без змін; перевірити з параметризованим SQL Prisma); slug → id окремим запитом перед стрічкою — широкий фільтр 64 → 25 мс; `total` — кеш ([D35](decisions/D35-caching-measure-first.md)) | > 5 000 новин або p95 `GET /posts` > 100 мс (M2.12) |
| ⭐ Пошук і список новин в адмінці на тисячах новин. Виміряно в M1.4.8.1 ([D47](decisions/D47-admin-posts.md); синтетичні 20 000 новин, 32 000 перекладів, схема `e2e`): пошук за заголовком — ~50–55 мс на запит (сторінка й `total`), бо `ILIKE '%…%'` сканує всі заголовки; без фільтрів — ~13 мс (сортування за `createdAt` без індексу). Частковий індекс у порядку списку `Post("createdAt" DESC, id DESC) WHERE "deletedAt" IS NULL` (виміряно там же, `CREATE INDEX` у транзакції з `ROLLBACK`) прискорює лише сторінку — без фільтрів 13 → 0,06 мс, з пошуком 55 → 3–7 мс; `total` з пошуком лишається ~55 мс. Обидва запити пошуку прискорить GIN-індекс триграм `PostTranslation(title gin_trgm_ops)` — `pg_trgm` працює й для `ILIKE` з `%` на початку (не виміряно: розширення на Supabase доступне, на dev-БД не встановлене; міграція — `CREATE EXTENSION` + індекс, спершу виміряти на копії). Вибір `pg_trgm` чи `tsvector` — окремим рішенням, разом з публічним пошуком: [`ideas.md`](ideas.md), «Пошук по новинах і індекс пошуку» | Пошук в адмінці > ~200 мс або > 50 000 новин |
| ⭐ Пошук клубів, коли збігів запиту більше за 200 (стеля `CLUB_SEARCH_CANDIDATES_MAX`, [D48](decisions/D48-competition-in-play.md)): ранжуються лише перші 200 за абеткою, тож клуб, що починається з запиту, але за абеткою далі, загубиться. Рішення — ранжування в SQL (`ORDER BY` «починається з запиту» з `LIMIT 20`, сирий запит) або `pg_trgm` | Клубів у БД — кілька сотень (зараз 186) |

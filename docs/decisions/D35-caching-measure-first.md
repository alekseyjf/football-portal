# D35 — Кеш: спершу вимірювання

- **Статус:** ✅ прийнято · 2026-10-08 · 👤 рішення власника (13.6)
- **Етап:** M2.12
- **Уточнює:** [🧭 п. 4, п. 14](v5-architecture-review.md)

## Рішення
- 👤 Спершу виміряти p95 ендпоінтів і сторінок; кешувати лише те, що справді повільне.
- 👤 Шари — по черзі, від дешевого: HTTP-кеш (`Cache-Control` / `s-maxage`) і ISR / revalidate у Next → in-memory кеш в API (`@nestjs/cache-manager`, TTL 30–60 с; інвалідація після `SyncRun` свого турніру — 🧭 п. 4) → Redis лише з кількома інстансами ([D41](D41-single-instance-scaling.md)).
- ⚠️ Нюанс: зараз усі сторінки динамічні (пояс беремо з cookie — 🧭 п. 14). ISR без зміни підходу до поясу не спрацює (тоді — форматування дат на клієнті після гідрації). Для SEO динамічний SSR не проблема — він індексується повністю.

## Чому
Кожен кеш додає інвалідацію — найчастіше джерело багів «чому таблиця стара?». Для порталу з десятком турнірів БД, найімовірніше, справляється сама.

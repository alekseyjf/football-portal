## Контекст
⚠️ Власник вважав, що коментарі вже як на YouTube, але в коді — справжнє дерево до 15 рівнів (`MAX_COMMENT_THREAD_DEPTH = 15`, `CommentThreadNode` рендерить відповіді рекурсивно). Soft delete ховає всю гілку під коментарем (P4-5); API віддає все дерево одним запитом без пагінації; лайки кожного коментаря — окремим HTTP-запитом (N+1: 100 коментарів = 100 запитів і ~200 SQL).

## Рішення

### Модель
- 👤 Один рівень: корені + відповіді під коренем. Відповідь на відповідь потрапляє в ту саму гілку з «@Ім'я» на початку.
- 👤 (OQ-3) Усі відповіді гілки — `parentId = rootId`, `depth = 1`. CHECK у `constraints.sql`: корінь — без `parentId` / `rootId`, `depth = 0`; відповідь — `parentId = rootId`, `depth = 1` (лише першого рівня).
- 👤 (OQ-3) Кому відповіли — два nullable-поля в тій самій міграції: `replyToUserId` (FK на `User`) і `replyToCommentId` (FK на `Comment`, `ON DELETE SET NULL`) — *чому* другий: сповіщення про відповідь і перехід до коментаря, на який відповіли, — у майбутньому ([`backlog.md`](../backlog.md)); колонка зараз дешевша за міграцію даних потім.
  - ⭐ `replyToUserId` — теж `ON DELETE SET NULL` (як `Post.pinnedById`): акаунт анонімізується, а не видаляється (D19), але фізичне видалення рядка `User` не повинно валити коментарі; ⭐ адресат — лише у відповіді (CHECK).
- 👤 Старий клієнт відповідає на відповідь (`parentId` = відповідь) — API записує в корінь гілки: `parentId = rootId`, `replyToCommentId` — відповідь, на яку відповіли, `replyToUserId` — її автор. Відповідь на корінь — без адресата.
- ⭐ «@Ім'я» не пишемо в текст коментаря: сайт показує його з профілю адресата, тож перейменування оновлює згадку, а видалений акаунт — «@Видалений користувач».
- 👤 Наявні дані не «сплющуємо»: на dev-БД лише тестові коментарі — їх видаляє разовий SQL **до** міграції (дамп + перевірка відновлення; перед SQL — усі посилання на коментарі: FK, поліморфні без FK, лічильники — щоб не лишилось «сиріт»). Міграція — лише схема: якщо глибокий рядок якось лишився, новий CHECK голосно впаде, а не зіпсує дані.

### Видалення (👤 2026-10-27)
- 👤 Відповідь — зникає; інші відповіді гілки лишаються, навіть ті, що згадували її автора (як на YouTube, У14).
- 👤 Корінь з живими відповідями — заглушка «Коментар видалено»: `deletedAt` стоїть, текст і автор у відповіді API приховані, відповіді лишаються. Корінь без відповідей — зникає повністю.
  - ⭐ «Зникає» — для читача: рядок лишається з `deletedAt` (soft delete, backend Rule 7), фізично — лише purge адміна (D20) — *чому:* модерація й майбутні скарги (M3.2) спираються на рядок.
  - ⭐ Заглушка — похідний стан, а не збережений: видалений корінь видно, поки в нього є живі відповіді (`replyCount > 0`); видалили останню — зникає й заглушка.
- ⭐ Адмін чужі коментарі не редагує — лише видаляє — *чому:* правка чужих слів від імені автора — погана практика модерації.
- ⭐ (M1.7.2) Розмова під заглушкою триває: відповідь на живу відповідь гілки — можна (гілка відкрита, поки корінь живий або є заглушкою), на саму заглушку — 404 `PARENT_COMMENT_NOT_FOUND` — *чому:* чужі відповіді лишились, щоб їх читали й відповідали; заглушка — не коментар.
- ⭐ (M1.7.2) `DELETE /comments/{id}` → `{ id }` (було `{ id, deletedCount }`: тепер завжди 1); `POST /comments` повертає коментар порції (`CommentItemDto`) — сайт M1.7.3 вставить свій новий коментар у кеш порції без перезапиту.

### Порції й сортування (👤 2026-10-27, OQ-3)
- 👤 Корені — порціями по 20, «Показати ще» (без номерів сторінок); відповіді згорнуті («▼ N відповідей») і вантажаться по 10, від старих до нових (як на YouTube).
- 👤 (2026-10-27, бриф M1.7.2) **Зараз — лише «Нові»:** корені `createdAt ↓ → id ↓`, відповіді `createdAt ↑ → id ↑`. Курсор — за ключем порядку (keyset), а не `OFFSET`. **Дублі між порціями неприпустимі** — на незмінних даних і при вставці / видаленні між запитами (e2e).
  - 👤 API розширюваний: `?sort=` є з першого дня й приймає лише `newest`, інше → 400 з переліком дозволених; сайт передає `sort` завжди. ⭐ Параметр обов'язковий — *чому:* значення за замовчуванням немає, тож коли з'являться «Популярні», відповідь клієнтам, що їх не просили, не зміниться.
  - 👤 Курсор — непрозорий base64url JSON `{ v: 1, sort, scope, createdAt, id }` (`scope` — `post:<id>`, `match:<id>` або `replies:<rootId>`); невалідний, з іншого `sort` чи іншої новини / матчу / гілки → 400 `COMMENT_CURSOR_INVALID`. Відповідь — `{ items, nextCursor | null }`, `limit` ≤ 50. `createdAt` — `timestamptz(3)`, курсор тримає мілісекунди: за рівного часу порядок — за `id` (unit і e2e).
  - 👤 Індекси «Нових» — одразу в міграції 0012, `EXPLAIN` — перевірка ([`football-plan.md`](../football-plan.md), M1.7.2). Коментар не знає новини чи матчу — лише тред (один на ціль), тож замість двох індексів (`postId` / `matchId`) — один частковий `("threadId", "createdAt" DESC, "id" DESC) WHERE "parentId" IS NULL`; відповіді — `(rootId, createdAt, id)`.
- 👤 **«Популярні» — M2.14**, окремим під-етапом, без зміни маршрутів і форми відповіді: ⭐ варіант А — знімок порядку на першому запиті (впорядковані id, топ-500 коренів, TTL 30–60 хв), `snapshotId` у курсорі `v: 2`, лайки в картках — свіжі; варіант Б (запасний) — `asOf` у курсорі, рейтинг за лайками до `asOf`. Там же — ранжування із загасанням у часі й вибір сортування за замовчуванням.
  - Замінює компроміс 2026-10-27 (бриф M1.7: «рідкісний пропуск під «Популярними» приймаємо, знімок коштує більше за користь») — 👤 дублів і пропусків не має бути й у «Популярних».
  - Складність переходу — невелика: курсор уже версійний і прив'язаний до `sort`, тож «Популярні» — нове значення `sort`, нова версія курсора й сховище знімка; «Нові» і сайт не змінюються.
- ⭐ Лайки — `likeCount` + `myReaction` разом з порцією коментарів (один запит `CommentLike where userId, commentId IN (…)`). ✅ M1.7.2.
- 👤 Сайт (M1.7.3): свій новий коментар — одразу нагорі при будь-якому сортуванні; коментарі вантажаться ліниво при прокрутці, не в SSR, скелетон — без зсуву макета; лічильник «N коментарів»; «Відповісти» на відповідь — чип «Відповідь @Ім'я ×» над полем (`aria-label` на «×»).
  - 👤 (2026-10-29, бриф M1.7.3) Лічильник — `commentCount` треду в кожній порції коренів (`GET /comments`), без змін БД: `CommentThread.commentCount` уже рахує живі корені й відповіді (заглушка — ні) у транзакції коментаря; рядок треду сервіс і так читає — без `COUNT(*)` на порцію.
  - 👤 (2026-10-29) `isLocked` у відповідь не віддаємо: увімкнути його нічим (lock / unlock M2.5 — відкладено), `POST` і далі відповідає 403 `COMMENT_THREAD_LOCKED` на закритий тред.
  - 👤 (2026-10-29) Старе дерево (`GET /comments/post|match/…`) прибрано разом із сайтом, одним PR: інших клієнтів немає.

### Редагування
- 👤 Свій коментар — протягом 15 хв, з позначкою «змінено» (`editedAt`, `timestamptz` — колонка вже є). 👤 (2026-10-27) Відредагований текст проходить ті самі перевірки й ліміти, що новий; лайки не скидаються.
- 👤 (2026-10-29, бриф M1.7.4) «Ті самі ліміти» уточнено: межі тексту — ті самі (один клас `CommentContentDto` для `POST` і `PATCH`), **пауза 60 с і burst на зміну не діють** — *чому:* одруківку виправляють одразу після відправки, а правки й так обмежують 15 хв і «лише своє»; зміна не пише `RateLimitEvent`. 👤 Активний бан на коментарі (`COMMENTS_SUSPENDED`) забороняє й зміну — *чому:* інакше забанений перепише свої свіжі коментарі на спам; читати можна.
- ✅ (M1.7.4) `PATCH /comments/{id}` `{ content }` → `CommentItemDto`: лише автор (чужий, і адміну, — 403 `COMMENT_EDIT_FORBIDDEN`), 15 хв від `createdAt` (далі — 403 `COMMENT_EDIT_WINDOW_CLOSED`), видалений чи заглушка — 404 `COMMENT_NOT_FOUND`, закритий тред — 403 `COMMENT_THREAD_LOCKED`, як для нового (адміну свій — можна). Той самий текст (після trim) — 200 без `editedAt`.
  - ⭐ Правило вікна — одне на API і сайт: `isCommentEditWindowOpen` / `commentEditWindowStart` у `packages/validation` (рівно 15 хв — уже закрите).
  - ⭐ Вікно, автор і «не видалено» — умова одного `UPDATE … WHERE` (backend Rule 10), а не перевірка перед записом — *чому:* правка на межі 15 хв чи паралельне видалення не проскочать між ними. Видалення, що встигло першим, перемагає: правка чекає на його блокування й отримує 404 (e2e відтворює це детерміновано); запис і читання відповіді — одна транзакція, тож видалення, що прийшло слідом, не підмінить у відповіді текст заглушкою.
- 👤 Сайт: «Редагувати» — на своєму, поки вікно відкрите за годинником браузера (без таймера-перемальовування); форма — на місці тексту з цим текстом; збережений коментар з відповіді API замінює свій у кеші порції — без перезапиту. Годинник читача відстав — після «Зберегти» API відмовляє, під полем «Час на зміну коментаря минув».
  - ⭐ «Редагувати» — у рядку дій поруч з «Відповісти», не в шапці біля «Видалити» — *чому:* на 320 px дві кнопки в шапці витіснили б ім'я автора.
  - ⭐ «(змінено)» — біля дати (`<time dateTime={editedAt}>`), точний час зміни — у підказці (`title`), як на YouTube.
  - ⭐ Адресат відповіді на відповідь під час зміни — чип без «×»: адресат — частина відповіді, а не тексту, правка його не змінює.

## Наслідки
- Purge відповіді — завжди «листок» (дітей за `parentId` у неї немає) — логіка purge спрощується; `MAX_COMMENT_THREAD_DEPTH`, `COMMENT_DEPTH_EXCEEDED` і рекурсивне піддерево прибрано (M1.7.2). Purge-thread кореня бере відповіді за `rootId` під блокуванням кореня: вставка відповіді спершу оновлює корінь, тож гілка в цей момент не росте.
- ⭐ (M1.7.2, замір) Індекси на FK `parentId` і `replyToCommentId`: purge фізично видаляє коментарі, і без індексу кожен видалений рядок перевіряє всю таблицю — на 657 тис. рядків 20 відповідей видалялись 3,3 с (таймаут транзакції Prisma — 5 с), з індексами 5 000 — 0,34 с.
- UI без рекурсії; на сторінці — один запит на порцію коментарів.
- Старий `GET /comments/post/:postId` (дерево) жив до M1.7.3: на «плоских» даних він давав 2 рівні, тож сайт між під-етапами працював. M1.7.3 прибрав його разом із `CommentThreadNode` і запитами `GET /likes/stats/comment/…` на кожен коментар.
- (M1.7.3) Свій коментар сайт уставляє в кеш порцій сам (корінь — нагорі, відповідь — у кінці розгорнутої гілки), а після видалення перечитує порції: що лишиться — заглушка, зник корінь, лічильники — вирішує API, тож ці правила живуть в одному місці.
- Документація коментарів (`CLAUDE.md`, `architecture.md`) — оновити.

## Розглянуті альтернативи
- Дерево (як зараз) — відхилено 👤.
- «Сплющити» наявні дані міграцією (адресат = автор колишнього батька) — так рекомендувалось 2026-10-08; 👤 2026-10-27 замінено видаленням тестових коментарів: реальних даних немає, а міграцію даних треба писати й тестувати.
- ⭐ Видалення кореня ховає всю гілку (рекомендація 2026-10-08) — 👤 2026-10-27 замінено заглушкою «Коментар видалено», якщо в кореня є відповіді: чужі відповіді не зникають через рішення автора кореня.
- `OFFSET` для порцій — відхилено: зсувається й від лайків, і від кожного нового коментаря; курсор «Нових» не зсувається взагалі, «Популярних» — лише від лайків.
- «Популярні» з курсором за ключем `likeCount` без знімка (рішення 2026-10-27, бриф M1.7) — 👤 2026-10-27 (бриф M1.7.2) замінено: дублі й пропуски неприпустимі, «Популярні» — зі знімком у M2.14.

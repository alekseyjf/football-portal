# D41 — Один інстанс API; Redis і окремий worker — за тригером

- **Статус:** ✅ прийнято · 2026-10-08 · 👤 рішення власника (9.2, 10.7)
- **Реалізує:** [🧭 п. 12](v5-architecture-review.md)

## Контекст
У пам'яті процесу живуть: ліміти запитів (throttler), черга football-data, майбутній кеш. Друга репліка API — це подвійні cron-и, розсинхрон лімітів і кешу.

## Рішення
- 👤 Поки що API — **один** інстанс; усе вищезгадане — у пам'яті процесу.
- 👤 Синк відокремлено структурно — **уже зроблено** (вимога 10.7): `FootballSyncModule`; cron (`football.cron.ts`) лише викликає сервіси синку; лок — `SyncRun` (`RUNNING` + частковий унікальний індекс + advisory-лок, завислі → `FAILED STALE`).
- Тригери:
  - більше одного інстансу або черги задач → Redis (throttler, лок, кеш);
  - окремий worker синку → нова точка входу (`NestFactory.createApplicationContext`) + прапорець, що вимикає cron в API-процесі;
  - worker і API обидва ходять до провайдера → спільна квота (у БД або Redis).

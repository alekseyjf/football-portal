# D30 — Тести й середовище розробки: без Docker локально, Docker — для деплою

- **Статус:** ✅ прийнято · 2026-10-08 · 👤 рішення власника (3.5–3.10, 10.8, У18) + ⭐ деталі · оновлено 2026-10-18 (👤 OQ-5: e2e локально — схема `e2e` у поточній БД)
- **Етап:** M1.3 (каркас e2e, Vitest), M1.10 (CI), M1.11 (Docker), M2.10 (Playwright)
- **Замінює:** [🧭 п. 9](v5-architecture-review.md) у частині «Docker для e2e локально» і «CI на старті»

## Контекст
У Фазах 2–5 сотні перевірок писались тимчасовими скриптами й видалялись. Власник хоче тести, які реально щось перевіряють, із запуском окремо для кожного модуля; локальну розробку — без Docker.

## Рішення
- 👤 Тести — лише змістовні (інваріанти, межі, гонки, права); порожніх «для галочки» не пишемо. Запуск окремо для модуля: `pnpm --filter @football-portal/api test -- posts`.
- 👤 Unit: jest (API), ⭐ Vitest (web).
- 👤 E2E API — постійний набір `apps/api/test/` на **окремій** БД:
  - у CI — тимчасовий Postgres у GitHub Actions (Docker там є «з коробки», на Маці не потрібен);
  - локально — 👤 (2026-10-18, OQ-5) без локальної БД: окрема схема `e2e` у поточній Supabase-БД, «обережно, щоб не зламати» справжні дані (`public`). Як це забезпечено — нижче, «Схема `e2e`».
- ⭐ Фейковий football-провайдер з «воротами» для детермінованих гонок — як у Фазі 5.
- 👤 Браузерні сценарії — Playwright (M2.10).
- 👤 Локально — `pnpm dev` + Supabase, без Docker; Docker — лише образ для деплою (M1.11).

## Схема `e2e` (M1.3.3, `apps/api/test/support/`)
- Схема — константа `e2e` у коді, а не налаштування: жоден рядок підключення чи змінна не спрямує в `public` ні запити застосунку, ні `DROP` / `TRUNCATE`.
- ⚠️ Адаптер Prisma 7 (`PrismaPg`) ігнорує `?schema=` у рядку підключення — `PrismaService` писав би в `public`. Тому e2e підміняють його своїм клієнтом: `PrismaPg(…, { schema: 'e2e' })` (запити Prisma кваліфіковані — `"e2e"."Post"`) + `search_path=e2e` при підключенні (сирий SQL застосунку пише таблиці без схеми); перед стартом — перевірка `current_schema()`. `DATABASE_URL` тест-застосунку нікуди не веде.
- Схему перебудовуємо з нуля на кожен прогін — одним запитом в одній транзакції з `SET LOCAL search_path` і перевіркою `current_schema()` до першої міграції (у міграціях є `UPDATE` без схеми). ⭐ Не `prisma migrate deploy`: той бере адресу з `prisma.config.ts` і `.env` (→ `public`).
- Підключення — `E2E_DATABASE_URL` (CI) або `DIRECT_URL` (session pooler); transaction pooler не годиться — `search_path` там не тримається між транзакціями. `.env` тести лише читають: у `process.env` (і в застосунок) він не потрапляє.
- Тести йдуть по одному (`maxWorkers: 1`): схема одна на всі файли; кожен файл починає з `resetE2eData`.
- Перевірено поломками: без `search_path` тести не стартують, з `search_path=public` перебудова відкочується; `public` після прогонів не змінився.

## Наслідки
- Тести не чіпають справжніх даних; кожен етап додає свої e2e разом із функціоналом.
- E2E потребують мережі й живої Supabase-БД (безкоштовний проєкт засинає після тижня без активності — тоді його відновлює власник). Схема `e2e` лежить поруч із даними тест-сервера, доки dev і test не розділено (OQ-8).

## Розглянуті альтернативи
- E2E на dev-Supabase в тій самій схемі — відхилено: там справжній синк і майбутні дані тест-сервера. Окрема схема `e2e` у тій самій БД — 👤 прийнято (2026-10-18).
- Postgres з Homebrew (`football_e2e`) — ⭐ пропонувався в OQ-5; 👤 відхилено: без локальної БД.
- docker-compose для розробки — відхилено 👤.

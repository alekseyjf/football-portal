# D30 — Тести й середовище розробки: без Docker локально, Docker — для деплою

- **Статус:** ✅ прийнято · 2026-10-08 · 👤 рішення власника (3.5–3.10, 10.8, У18) + ⭐ деталі
- **Етап:** M1.3 (каркас e2e, Vitest), M1.10 (CI), M1.11 (Docker), M2.10 (Playwright)
- **Замінює:** [🧭 п. 9](v5-architecture-review.md) у частині «Docker для e2e локально» і «CI на старті»

## Контекст
У Фазах 2–5 сотні перевірок писались тимчасовими скриптами й видалялись. Власник хоче тести, які реально щось перевіряють, із запуском окремо для кожного модуля; локальну розробку — без Docker.

## Рішення
- 👤 Тести — лише змістовні (інваріанти, межі, гонки, права); порожніх «для галочки» не пишемо. Запуск окремо для модуля: `pnpm --filter @football-portal/api test -- posts`.
- 👤 Unit: jest (API), ⭐ Vitest (web).
- 👤 E2E API — постійний набір `apps/api/test/` на **окремій** БД:
  - у CI — тимчасовий Postgres у GitHub Actions (Docker там є «з коробки», на Маці не потрібен);
  - локально — ⭐ Postgres з Homebrew або окрема схема (❓ OQ-5).
- ⭐ Фейковий football-провайдер з «воротами» для детермінованих гонок — як у Фазі 5.
- 👤 Браузерні сценарії — Playwright (M2.10).
- 👤 Локально — `pnpm dev` + Supabase, без Docker; Docker — лише образ для деплою (M1.11).

## Наслідки
- Тести не чіпають справжніх даних; кожен етап додає свої e2e разом із функціоналом.

## Розглянуті альтернативи
- E2E на dev-Supabase — відхилено: там справжній синк і майбутні дані тест-сервера.
- docker-compose для розробки — відхилено 👤.

# D47 — Новини в адмінці: список сторінками з пошуком, новина для форми, формат чипів

- **Статус:** ✅ прийнято · 2026-10-21 · 👤 рішення власника (два PR, пошук будь-якою мовою, формат чипів турніру й клубу, пошук клубів лише для ADMIN) + ⭐ деталі API · ✅ API постів — M1.4.8.1 · ✅ турніри й клуби для форми — M1.4.8.2 ([D48](D48-competition-in-play.md))
- **Етап:** M1.4.8.1 (пости для адмінки), M1.4.8.2 (турніри й клуби для форми), M1.5 (форма й список в адмінці)
- **Уточнює:** [D38](D38-news-list-load-more.md) — offset-пагінація; [D45](D45-tags.md) — теги в адмінці; [D46](D46-post-feed-filters.md) — підказка турнірів клубу; [P3-1](v5-content.md) — запланована новина виходить сама, без cron

## Контекст
Формі редагування (M1.5) потрібна новина з усім, що вона редагує, а `POST` / `PUT /posts` повертають `AdminPostDto` — без текстів і зв'язків. `GET /posts/admin/all` віддавав усі новини одним масивом, без фільтрів. Вибір тегів, турнірів і клубів у формі показує вибране «чипами» — у новині й у результатах вибору формат має бути один.

## Рішення
👤 **Два PR** (2026-10-21): M1.4.8.1 — пости для адмінки; M1.4.8.2 — турніри й клуби для форми (бере формат чипів з M1.4.8.1).

⭐ **`GET /posts/admin/{id}`** → `AdminPostDetailDto`: новина будь-якого статусу, і чернетка; видалена чи неіснуюча → 404 `POST_NOT_FOUND`. Поля рядка списку + `coverImageCredit`, `videoUrl`, `sourceUrl`, `sourceName`; переклади всіма мовами з текстом (`title`, `excerpt`, `content`, `coverImageAlt`) у порядку мов сайту; теги, турніри, клуби — чипами. *Чому окремий ендпоінт, а не повний пост у відповіді `POST` / `PUT`:* форма читає новину перед правкою, після збереження — refetch (TanStack Query); запис лишається легким.

👤 **Формат чипів** — однаковий у новині й у виборі:

| Чип | Поля | DTO · select | Де ще |
|---|---|---|---|
| Турнір | `id`, `slug`, `name` | `CompetitionRefDto` · `COMPETITION_REF_SELECT` (`football/football-refs.ts`) | вибір турнірів, турніри клубу в пошуку (M1.4.8.2 ✅, [D48](D48-competition-in-play.md)) |
| Клуб | `id`, `slug`, `name`, `crestUrl` | `ClubRefDto` · `CLUB_REF_SELECT` (`football/football-refs.ts`) | пошук клубів (M1.4.8.2 ✅, [D48](D48-competition-in-play.md)) |
| Тег ⭐ | `id`, `slug`, `translations` (назви всіма мовами) | `AdminTagRefDto` · `ADMIN_TAG_REF_SELECT` (`tag.repository.ts`, поруч з `publicTagSelect`) | `AdminTagDto` — той самий тег + `postCount`: варіант у виборі тегів і відповідь `POST /tags` |

- ⭐ Тег — з назвами всіма мовами, а не однією `name`. *Чому:* вибір тегів працює з `AdminTagDto` (`GET /tags/admin/all`, `POST /tags`) — чип і варіант вибору мають одну форму; JSON `AdminTagDto` не змінився.
- ⭐ DTO і select-и — у модулях своїх сутностей (football, tags), пости їх імпортують. *Чому:* content → football можна, навпаки — ні (🧭 п. 1); M1.4.8.2 бере ті самі класи. Select-и football — окремим файлом `football-refs.ts`, а не з `persistence/`: інші модулі не залежать від внутрішнього розкладу football (clean-code Rule 2).

⭐ **`GET /posts/admin/all?page=&limit=&status=&search=`** → `{ data, total, page, limit, totalPages }`, як стрічка (D38): `limit` — 20 за замовчуванням, до 100 (`ADMIN_POSTS_PAGE_LIMIT_DEFAULT` / `_MAX` — `packages/validation`, з першого бере й адмінка); нові першими (`createdAt desc, id desc`); видалених немає.
- ⭐ **Статус — як бачить редактор:** `PUBLISHED` — і запланована новина, чия дата настала (на сайті вона вже є, а в БД лишається `SCHEDULED` — cron-а немає, P3-1); `SCHEDULED` — лише ті, що чекають своєї дати; `DRAFT`, `ARCHIVED` — як у БД. *Чому:* адмінка підписує таку новину «Published» (`isLive`) — фільтр «Scheduled» з новинами «Published» плутав би. Кожна новина — рівно в одному статусі: у `PUBLISHED` / `SCHEDULED` дата є завжди (CHECK `Post_published_has_date_check`). Правило — чиста функція `adminPostListWhere` (`posts/admin-post-filter.ts`); «на сайті» — той самий `livePostWhere`, що й `isLive`. e2e звіряє фільтр із підписом адмінки: кожен рядок фільтра адмінка підписує цим статусом.
- 👤 **Пошук** — частина заголовка будь-якою мовою, без урахування регістру; 1–100 символів після trim (`ADMIN_POSTS_SEARCH_MAX_LENGTH`); порожній, з самих пробілів чи повтор параметра → 400. Зі статусом — «і».
- ⭐ **`%` і `_` — як текст.** Prisma 7 підставляє `contains` у `ILIKE '%' || $1 || '%'` без екранування (перевірено на SQL, який вона будує): «100%» знайшов би «1000 fans», `_` — будь-який символ. Екрануємо `\`, `%`, `_` самі — `containsIgnoringCase` (`prisma/prisma-text-search.ts`; її ж бере пошук клубів).
- **Кирилиця:** регістр ігнорує локаль БД. dev-БД — PostgreSQL 17, `datctype = en_US.UTF-8`, провайдер ICU (`en-US`): «динамо» знаходить «Динамо» (e2e). ⚠️ БД тест-сервера й CI — з UTF-8 локаллю (не `C`); e2e це перевірить.
- ⭐ **Індексу для пошуку немає** — виміряно (нижче).

⭐ **`PostService` поділено за use case** (clean-code Rule 6, як football): `PublicPostService` — стрічка й новина за номером; `AdminPostService` — список і новина для форми; `PostEditorService` — створення, зміна, видалення (правила D23–D26, D44). Репозиторії — `PublicPostRepository` (публічні читання) і `AdminPostRepository` (читання адміном і записи). Поведінка й контракт поділу не змінились (e2e — 90 з 90, `openapi.json` — побайтно той самий).

## Плани запитів (`EXPLAIN ANALYZE`)
Синтетичні 20 000 новин (32 000 перекладів, 15 MB) у схемі `e2e` dev-БД, справжній `AdminPostRepository` і SQL Prisma 7 (`EXISTS (… "title" ILIKE …)`); сторінка й `total` — паралельні запити, час — кожного:
- без фільтрів — сторінка ~13 мс, `total` ~6 мс (сортування за `createdAt` без індексу);
- пошук — ~50–55 мс кожен, і без збігів: послідовний скан усіх заголовків (часте слово, рідкісне, кирилиця, разом зі статусом);
- статус `SCHEDULED` — ~1 мс (індекс `Post(status, deletedAt, publishedAt)`);
- гіпотеза — частковий індекс `Post("createdAt" DESC, id DESC) WHERE "deletedAt" IS NULL` (у транзакції з `ROLLBACK`): сторінка без фільтрів — 13 → 0,06 мс, з пошуком — 55 → 3–7 мс, але `total` з пошуком лишається ~55 мс.

Для адмінки (кілька редакторів, пошук із затримкою вводу) цього досить. Що прискорить — [`backlog.md`](../backlog.md), «Масштабування».

## Як роблять сильні команди
- WordPress REST API: `/wp/v2/posts?status=draft&search=…&page=2&per_page=20` — пошук і статус в одному списку, `X-WP-Total` / `X-WP-TotalPages`.
- Ghost Admin API: `GET /posts/?filter=status:scheduled&page=2` і окремий `GET /posts/{id}/` з усіма полями для редактора.

## Наслідки
- ⚠️ Зламна зміна для адмінки: `GET /posts/admin/all` — сторінка замість масиву. Список адмінки оновлено в тому ж PR: сторінки по 20, «Newer / Older»; фільтр і пошук у UI — M1.5.
- Форма M1.5: новина й чипи — з `GET /posts/admin/{id}`; після збереження — refetch. Відповідь віддає й переклад вимкненою мовою, якщо такий збережено, — форма надсилає лише увімкнені мови (інакше 400 `UNSUPPORTED_LANGUAGE`).
- `?page=` у всіх списках — одна межа `PAGE_NUMBER_MAX` (`packages/validation`).

## Розглянуті альтернативи
- Повний пост у відповіді `POST` / `PUT` — відхилено: важчий кожен запис, а форма й так читає новину окремо.
- Фільтр за статусом у БД — відхилено: «Scheduled» показував би новини, які адмінка підписує «Published».
- Пошук лише за англійським заголовком — 👤 відхилено: українську новину шукають українською.
- Тег-чип `{ id, slug, name }` з англійською назвою — відхилено: вибір тегів працює з `AdminTagDto` (усі мови), тож форм чипа було б дві.
- Індекс `pg_trgm` одразу — відхилено до потреби: ~50 мс на 20 000 новин; розширення на dev-БД доступне, але не встановлене.
- Full-text (`tsvector`) — це для пошуку на сайті ([`ideas.md`](../ideas.md)); адмінці потрібна підстрока, а не морфологія.

# D56 — Головна новина: редактор закріплює одну живу новину, хто й коли — лише в адмінці

- **Статус:** ✅ прийнято · 2026-10-26 · 👤 рішення власника (бриф M1.6.3 і M1.6.4: закріплює ADMIN, лише жива новина, зміни публікації знімають закріплення, заміна з чесним підтвердженням, інваріант — частковий унікальний індекс; відповіді на ⭐ кроку «Коміт 2»: індекс і в міграції, і в `constraints.sql`, `ON DELETE SET NULL`, ідемпотентний відкат, поділ «API + сайт» / «адмінка»; хто й коли закріпив — лише в адмінці) + ⭐ деталі · ✅ M1.6.4
- **Етап:** M1.6.4; кеш і інвалідація головної — M2.12 ([`backlog.md`](../backlog.md), «Кеш головної й новин»); «закріпити під час виходу», виділення закріпленої понад 24 год, окрема роль — [`backlog.md`](../backlog.md)
- **Уточнює:** [D55](D55-home-page.md) — головна новина (до M1.6.4 — найсвіжіша); P3-1 — жива новина (`livePostWhere`); [D19](v5-identity.md) — акаунт анонімізується, рядок `User` лишається

## Контекст
З M1.6.3 головна новина — найсвіжіша (`GET /posts?limit=7`, перша з семи). Редакції потрібно ставити на головну важливу новину, навіть коли після неї вийшли інші, — як «закріпити» в Instagram. Закріплення — стан новини, який змінює ще й публікація: зняту з публікації чи заплановану в майбутнє новину сайт не покаже, і головною вона бути не може.

## Рішення

### Модель (міграція 0011)
- 👤 `Post.pinnedAt` — `timestamptz(3)` (закріпили — `now()`, відкріпили — `null`), `Post.pinnedById` — FK на `User`: хто закріпив.
- 👤 **Не більше однієї закріпленої — тримає БД:** частковий унікальний індекс `Post_single_pinned_idx` на сталому ключі `((true)) WHERE "pinnedAt" IS NOT NULL` — другий закріплений рядок порушує унікальність. Як «одна default-мова» й «один поточний сезон»: інваріант не залежить від того, чи правильно написана транзакція. Індекс — і в міграції 0011, і в `constraints.sql` (👤 однакова назва, `IF NOT EXISTS`): застосовує його міграція, а `constraints.sql` — копія для squash. `migrate diff` його не бачить і видалити не пропонує (перевірено на схемі `e2e`).
- 👤 `pinnedById` — `ON DELETE SET NULL`: акаунт не видаляється, а анонімізується (D19) — ім'я стане «Deleted user»; SET NULL — лише на випадок фізичного видалення рядка (ручний SQL), і закріплення від цього не зникає. ⭐ Індексу на `pinnedById` немає — не-null там щонайбільше один рядок, а `User` фізично не видаляють.
- 👤 **Відкат — ідемпотентний SQL** (індекс → FK → колонки, кожне з `IF EXISTS`): `migrate deploy` міграцію в транзакцію не загортає. ⚠️ Після відкату успішно застосованої міграції — `UPDATE "_prisma_migrations" SET rolled_back_at = now()`, а не `prisma migrate resolve --rolled-back`: той працює лише для **невдалої** міграції (P3012 «not in a failed state»), а `migrate status` ручного відкату не бачить — перевірка `migrate diff` зі схемою `master` ([`v5-foundation.md`](v5-foundation.md), розділ 11; перевірено на тимчасовій схемі).

### Правила (`posts/post-pin.ts`, чисті функції з unit)
- 👤 **Закріпити можна лише живу новину** (`decidePin`): чернетка, ще не випущена запланована, архівна → 409 `POST_NOT_LIVE` — *чому:* інакше до виходу запланованої головною тихо стала б найсвіжіша. Запланована, чия дата настала, — жива.
- 👤 **Зміни публікації знімають закріплення в тому ж записі** (`unpinsOnPublicationChange`, `PUT /posts/{id}`): зняли з публікації, в архів, перенесли в майбутнє; видалили (`DELETE /posts/{id}`) — теж. *Чому:* бейдж в адмінці не бреше, а повернута в публікацію новина не стає головною потай. Правка тексту живої (публікація та сама) закріплення не чіпає.
- 👤 **Заміна — лише підтверджена:** тіло `POST /posts/{id}/pin` — `{ replacesPostId }`, обов'язкове (і `null` — «закріпленої не бачив» — теж явно). Закріплена вже інша (друга вкладка, другий редактор) → 409 `PINNED_POST_CHANGED`, адмінка питає заново.
- ⭐ Уже закріплена → 200 без змін: хто й коли закріпив лишаються — *чому:* бажаний стан уже є, а чесний час закріплення не переписується повтором.

### API
- 👤 `POST /posts/{id}/pin` і `DELETE /posts/{id}/pin` — `@AdminOnly()` (закріплює той, хто публікує; окрема роль — backlog). Відповідь — рядок адмінки `AdminPostDto` (з `pinnedAt`, `pinnedBy`): адмінка кладе його в кеш, а не вгадує стан. ⭐ Код успіху — 200 (дія над наявною новиною, не створення). Відкріпити не закріплену — 200 без змін; немає чи видалена — 404.
- 👤 **Заміна — одна транзакція** (`PostPinService`): блокування `FOR NO KEY UPDATE` — спершу новина, яку закріплюють (видалена → 404, перевірка живої — на заблокованому рядку), потім закріплена; зняти попередню → закріпити нову. Порядок без циклу: закріплену змінює лише той, хто тримає її рядок. Паралельне закріплення, якого транзакція не бачила (`READ COMMITTED`), зупиняє індекс → 23505 → той самий 409 `PINNED_POST_CHANGED` (назву індексу адаптер Prisma лишає лише в тексті помилки — `isUniqueViolationOfIndex`, `prisma-errors.ts`). Обидві гонки — у e2e детерміновано.
- ⭐ **Закріплення не зсуває `updatedAt`** — записи сирим `UPDATE` (`@updatedAt` Prisma зсунув би): `updatedAt` — дата збереження тексту, адмінка показує її як «Saved …».
- 👤 `GET /posts/home?lang=` → `{ lead, latest }`: головна — закріплена (з правилом стрічки `publicPostWhere`), інакше найсвіжіша; `latest` — шість найсвіжіших без неї (`pickHomePosts`: сім найсвіжіших мінус головна — дубля немає за побудовою). Два запити паралельно — закріплена й сім найсвіжіших.
- 👤 **Хто й коли закріпив — лише в адмінці:** `pinnedAt` і `pinnedBy` (`PublicAuthorDto`; `null` — не закріплена або рядок `User` видалено фізично) — у рядку `GET /posts/admin/all`, у `GET /posts/admin/{id}` і у відповідях записів; публічні `GET /posts`, `GET /posts/home`, `GET /posts/{number}` цих полів не віддають (e2e: полів немає, контракт без `additionalProperties`).
- 👤 `GET /posts/admin/pinned` → `{ post: AdminPostDto | null }` — закріплена для тексту підтвердження (може бути не на поточній сторінці списку).

### Сайт
- Головна бере `GET /posts/home` (`homeNewsQueryOptions`, той самий ключ кешу `['posts', 'home', lang]`); розкладка D55 без змін. Кешу сторінок немає (усі запити — `no-store`), тож закріплення видно з наступного відкриття; інвалідація кешу на подію закріплення — разом з кешем (M2.12).

## Наслідки
- Нова причина зміни рядка `Post` — закріплення: кожен запис, що робить новину неживою, знімає його в тому самому оновленні (сьогодні — `PUT` і `DELETE /posts/{id}`; новий шлях зміни статусу — теж).
- Головна сайту — два запити до БД замість одного (паралельно).
- Сирий SQL у записах закріплення — таблиці без схеми, як інші блокування (`search_path`).

## Розглянуті альтернативи
- **Лише транзакція, без індексу** — інваріант тримається, поки кожен запис іде через сервіс; ручний SQL чи помилка в новому коді дали б дві головні, і сайт показав би випадкову.
- **Окрема таблиця `HomeLead` (один рядок)** — інваріант простіший, але «хто й коли» і зняття при зміні публікації тоді — у двох таблицях з окремими записами; поле поста знімається тим самим `UPDATE`.
- **Закріпити заплановану заздалегідь** — головною до виходу стала б найсвіжіша без попередження; «закріпити під час виходу» — backlog.
- **`updatedAt` зсувається при закріпленні (Prisma `update`)** — «Saved …» у формі показував би час закріплення як час збереження тексту.
- **`pinnedAt` / ім'я в публічних відповідях** — сайту це не потрібне, а ім'я редактора — внутрішня інформація редакції.

# D61 — Окрема БД тест-сервера: копія даних розробки, міграції в збірці Render, Data API вимкнено

- **Статус:** ✅ прийнято · 2026-11-07 · 👤 рішення власника (OQ-8, бриф після рев'ю M1.11) + ⭐ деталі · код — PR 1 M1.11 (`render.yaml`, `pnpm db:copy-to-test`); ⏳ наживо — під час створення сервісів (M1.11, «Порядок», крок 2)
- **Етап:** M1.11 (PR 1, створення сервісів, M1.11.5, M1.11.8, M1.11.9)
- **Замінює:** [D58](D58-test-hosting.md), розділ «БД» (одна БД для тесту й розробки, міграції з локальної машини). **Закриває** [OQ-8](../open-questions.md). **Уточнює:** backend Rule 16 і [`rules/process.md`](../rules/process.md) (міграції), [D36](D36-sync-operations.md) (чому `SyncRunTracker` закриває лише свої запуски), [D30](D30-testing-and-local-env.md) (схема `e2e`)

## Контекст
За D58 тест-сервер і локальна розробка працювали з однією Supabase, а щоб не зламати тест, діяли суворі правила міграцій. Рев'ю M1.11 показало, що ціна спільної БД вища за ці правила:
- воркер розкладу ([D57](D57-scheduled-publishing.md)) працює в кожному процесі API: локальний API публікує заплановану новину тесту й шле вебхук своєму web, а сайт тесту дізнається про неї лише за TTL (5 хв); правка з локальної адмінки так само не оновлює кеш тесту;
- секрет не може бути свій для середовища: `EMAIL_HASH_SECRET` прив'язаний до даних (HMAC пошт у `BlockedEmail`), тож мав би бути однаковим на Render і локально — виняток з [`rules/security.md`](../rules/security.md);
- демо замовнику показувало б дані розробки, а експеримент на машині розробника (міграція, сід, `reset`) ламав би сервер тестувальників.

## Рішення

### Дві БД
- 👤 Тест-сервер — **новий проєкт Supabase** (Free, Франкфурт, як Render і Vercel). Нинішня БД — лише для розробки (і схеми `e2e`).
- 👤 Старт тестової БД — **копія всіх даних** БД розробки: `pnpm db:copy-to-test` (`apps/api/scripts/copy-db-to-test.mjs`), один раз, до створення сервісу Render. Далі БД живуть окремо: новини для демо — в адмінці тесту.
  - Схема `public` з даними й `_prisma_migrations`: `pg_dump --schema=public --no-owner --no-privileges`, без схеми `e2e` і службових схем Supabase. Відновлення — `psql -v ON_ERROR_STOP=1 --single-transaction` разом із чисткою: впало будь-що — ціль лишається порожньою, і запуск можна повторити.
  - ⭐ Даних `AuthSession`, `RateLimitEvent`, `BlockedEmail` копія не бере (`--exclude-table-data`): їх немає навіть у тимчасовому файлі, а таблиці в цілі є, порожні. *Чому:* сесії й паузи коментарів — розробки, а HMAC пошт порахований секретом розробки й на тесті ні з чим не збігся б. `SyncRun` у стані `RUNNING` → `FAILED` («COPIED: …») — інакше лок синку тесту чекав би до 10 хв.
  - Запобіжники (зрозуміла помилка й вихід):
    - ціль — не джерело: хост, порт, БД і **користувач** — *чому користувач:* пулер Supabase має один хост на всі проєкти регіону, а проєкт видно лише з імені `postgres.<ref>`;
    - у `public` цілі немає таблиць і типів — повторний запуск чи не та БД (та сама через інший порт) відмовляють ще до дампу;
    - `pg_dump` / `psql` ≥ 17 (і не молодші за сервер джерела) — підказка `brew install libpq`; скрипт знаходить їх і поза PATH (keg-only Homebrew), обидва — з однієї теки;
    - ціль — не старша версія Postgres, ніж джерело.
  - Розширення, від яких залежать об'єкти `public` джерела (`pg_depend`), скрипт вмикає в цілі в тих самих схемах до відновлення. Зараз таких немає: розширення Supabase — у схемі `extensions`, і `public` ними не користується.
  - ⭐ `pg_dump` зі `--schema=public` пише `CREATE SCHEMA public;`, а в будь-якій новій БД `public` уже є — скрипт прибирає цей рядок. З ним psql зупинився б на першому ж операторі (знайдено на репетиції 2026-11-07).
  - Адреса тестової БД — з прихованого запиту (або `TEST_DIRECT_URL` у команді), не з файлу. Паролі — лише в змінних середовища `pg_dump` / `psql` / Prisma, не в аргументах; у виводі — `***`.
  - Перевірка наприкінці: рядки кожної таблиці «джерело | ціль» (джерело — з дампу: `pg_dump` читає один знімок БД, тож кількість точна) і `prisma migrate status` по цілі.

### Міграції тестової БД — у збірці Render
- 👤 `buildCommand` — `pnpm build:api && pnpm db:migrate`: `prisma migrate deploy` через `DIRECT_URL` (`prisma.config.ts`: `DIRECT_URL || DATABASE_URL`) лише після успішної збірки. `.env` не потрібен — перевірено 2026-11-07 (`migrate status` без файлу, лише зі змінною).
  - *Чому в збірці:* pre-deploy команди Render Free не має. При старті процесу міграцію запускав би кожен рестарт (а Render Free перезапускає будь-коли), невдала — сервер не стартує; ще й SIGTERM ішов би обгортці, а не процесу API (D36).
  - Ціна:
    - міграція застосується й тоді, коли новий процес потім не пройде health check;
    - ~1 хв деплою старий код працює вже з новою схемою;
    - відкат у Render (без збірки) міграцію не відкочує.
  - Тож для тесту лишається **expand → contract** (backend Rule 16). Невдала міграція — збірка червона, тест працює на старому коді; що робити — runbook (M1.11.9).
- 👤 `DIRECT_URL` на Render — **session pooler** (`:5432`, `*.pooler.supabase.com`), лише для міграцій; застосунок читає лише `DATABASE_URL` (transaction pooler, `:6543`). *Чому не пряме з'єднання* `db.<ref>.supabase.co`: воно лише IPv6, а з Render вихідного IPv6 немає.
- БД розробки більше не спільна: `prisma migrate dev` на ній дозволено, `pnpm db:migration:new` лишається простим способом (SQL без БД). Ворота перед кожною міграцією dev-БД (`pg_dump`, «ок» власника на SQL, «expand — до злиття») були лише через тест — прибрано.

### Безпека
- 👤 **Data API вимкнено** в обох проєктах: Integrations → Data API → Enable Data API; новий проєкт — одразу при створенні («Advanced Options»). *Чому:* API ходить у БД лише через Prisma, а REST / GraphQL Supabase — ще один вхід до таблиць з публічним ключем `anon`; RLS у таблицях Prisma немає.
- 👤 Секрети — свої для кожного середовища, без винятків: `EMAIL_HASH_SECRET` тесту — новий (у копії `BlockedEmail` порожня).
- Пароль адміна в копії — той самий, що в розробці: змінити одразу після копії. Зміни пароля в адмінці ще немає — bcrypt-хеш локально й `UPDATE` у SQL Editor тестового проєкту (план M1.11, «Порядок», крок 2; сама функція — [`backlog.md`](../backlog.md)).

### Що лишається як було — і чому
- `SyncRunTracker` закриває лише свої запуски: при деплої без простою Render ~1 хв тримає старий і новий процес на одній БД — чужий запуск ще живий.
- `FOOTBALL_SYNC_CRON_ENABLED=false` локально ([D36](D36-sync-operations.md)): причина — спільний ключ football-data (ліміт 10 запитів / хв), а не БД. Дані футболу в БД розробки — кнопкою «Синк» в адмінці.
- e2e — у схемі `e2e` БД розробки (`E2E_DATABASE_URL` / `DIRECT_URL`), у CI — свій Postgres.

## Наслідки
- Мінуси:
  - БД розробки ніхто не пінгує (keep-alive і монітор тримають тестову): Free-проєкт засне після 7 днів без активності — відновлення вручну в дашборді Supabase;
  - Free дає 2 активні проєкти — обидва зайняті. Для проду (M3.1) — Pro або розробка на локальному Postgres у Docker;
  - на Free Supabase автоматичних бекапів не робить — до тижневого бекапу (M1.11.8) тестова БД має лише одну страховку: БД розробки, з якої її скопійовано.
- Міграції тестової БД — без ручного кроку: злиття PR → зелений CI → збірка Render мігрує й деплоїть.
- Squash міграцій (M3.1): процедуру з `migrate reset` можна виконати на БД розробки; що робити з тестовою (`_prisma_migrations` під новий `0001_init`) — вирішити там.

## Розглянуті альтернативи
- **Лишити одну БД (D58)** — воркер розкладу публікує новини тесту з машини розробника, спільний `EMAIL_HASH_SECRET`, дані розробки в демо.
- **Нинішня БД — тестова, для розробки — новий проєкт** (рекомендація OQ-8) — без перенесення даних, але розробка починала б з порожньої БД (сід, турніри, синк заново). Власник обрав копію в новий проєкт.
- **Тестова БД з нуля (міграції й сід)** — демо без даних: новини, теги, користувачі — заново.
- **Міграції при старті процесу** (`prisma migrate deploy && node …`) — див. «Чому в збірці».
- **Розробка на локальному Postgres у Docker** — без другого проєкту Supabase, але Docker на машині розробника ще немає; повернемось у M3.1.

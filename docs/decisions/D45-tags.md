# D45 — Теги: «будь-який» у фільтрі, сторінка тегу, slug з EN-назви, видалення каскадом

- **Статус:** ✅ прийнято · 2026-10-21 · 👤 рішення власника (OQ-1, а–в) + ⭐ деталі API · ✅ API й міграція `0009_tag_constraints` — M1.4.6
- **Етап:** M1.4.6 (API), M1.4.7 (фільтри стрічки), M1.5 (сторінка «Теги» й пікер в адмінці), M1.6 (теги-посилання), M1.8 (noindex), M2.13 (сторінка тегу й sitemap тегів — 👤 2026-10-24, [D51](D51-admin-tags.md))
- **Уточнено:** [D51](D51-admin-tags.md) (2026-10-24) — назва тегу обома мовами, адреса сторінки тегу — `publicTagPath`
- **Уточнює:** [D17](v5-foundation.md) (`TagTranslation`), [OQ-1](../open-questions.md), [план](../football-plan.md) M1.4.6

## Контекст
Схема тегів є з v5 (D17): `Tag { id, slug @unique, createdAt }`, назви — `TagTranslation { tagId, languageCode, name }`, зв'язок — `PostTag` з `onDelete: Cascade` з обох боків. Пости вже приймають `tagIds` (P3-8: ≤ 20, неіснуючий → 400 `UNKNOWN_TAG`) і віддають теги в стрічці й новині. API для самих тегів не було; OQ-1 (як фільтрувати кількома тегами, чи потрібна сторінка тегу, чи створювати тег з форми новини) чекав рішення до M1.4.6.

## Рішення
👤 **OQ-1** (2026-10-21):
- (а) Кілька тегів в одному фільтрі — **«будь-який»** (АБО), між різними фільтрами (тег, ліга, клуб) — **«і»**. Реалізація — M1.4.7, [D46](D46-post-feed-filters.md).
- (б) Окрема сторінка тегу **`/{locale}/news/tag/{slug}`** — M1.6; сторінка тегу без опублікованих новин — `noindex` (M1.8). 👤 2026-10-24 ([D51](D51-admin-tags.md)): сторінка — після виходу сайту на тест (M2.13), з описом тегу й SEO-полями; до того теги ведуть у фільтр `/news?tags=` (`noindex`).
- (в) Тег можна створити **прямо з форми новини** (M1.5): `POST /tags` повертає створений тег.

⭐ **API (M1.4.6)** — модуль `src/tags/`:

| Ендпоінт | Хто | Що віддає |
|---|---|---|
| `GET /tags?lang=` | публічно | `TagDto[]` — теги з опублікованими новинами |
| `GET /tags/{slug}?lang=` | публічно | `TagDto` — будь-який тег (для сторінки тегу); невідомий → 404 `TAG_NOT_FOUND`, slug не того формату → 400 |
| `GET /tags/admin/all` | ADMIN | `AdminTagDto[]` — назви всіма мовами й `postCount` |
| `POST /tags` | ADMIN | `AdminTagDto` (201) |
| `PUT /tags/{id}` | ADMIN | `AdminTagDto` |
| `DELETE /tags/{id}` | ADMIN | `{ id }` |

- ⭐ **Slug — з EN-назви** (`slugify`, спільний з новинами: `src/common/slug.ts`) або явний при створенні; **після створення не змінюється** — `PUT` його не приймає. *Чому:* адреса тегу — у посиланнях і в пошуку; явний slug — для коротшої адреси й для EN-назви без латиниці.
- ⭐ **Зайнятий slug → 409 `TAG_SLUG_TAKEN`**, без суфікса. *Чому:* той самий slug — та сама тема; `transfers-2` розколов би новини однієї теми на дві сторінки. Попереднього `SELECT` немає: перевіряє унікальний індекс `Tag.slug`, тож паралельне створення того самого тегу теж дає 409, а не 500.
- ⭐ **EN-назва без латиниці й без slug-а → 400 `TAG_SLUG_REQUIRED`.** *Чому:* у новини fallback `post` нешкідливий (новину визначає номер, D24), а тег визначає slug — усі такі теги отримали б один.
- ⭐ **Назви — те саме правило мов, що й переклади новини** (D23, P3-3): EN обов'язкова, лише увімкнені мови, кожна один раз; ті самі коди (`DEFAULT_TRANSLATION_REQUIRED`, `UNSUPPORTED_LANGUAGE`, `DUPLICATE_TRANSLATION_LANGUAGE`). Правило — `findTranslationLanguagesError` (`languages/translation-languages.ts`, раніше `findPostTranslationsError` у постах). `PUT` — upsert за мовою, видалити назву не можна (як переклад, P3-5). Назва — 2–50 символів після trim (`TAG_NAME_*`, `packages/validation`). *Чому:* це одне правило D23 / D17; дві копії розійшлися б. 👤 2026-10-24 ([D51](D51-admin-tags.md)): у тегу обов'язкові назви всіма увімкненими мовами (EN і UK) — те саме правило з `required: 'all'`, код `ALL_TRANSLATIONS_REQUIRED`.
- ⭐ **Публічний список — лише теги, у яких є новина зі стрічки** (`publicPostWhere` — те саме правило, що й `GET /posts`), за абеткою назви мовою запиту (`Intl.Collator`). Назва — мовою запиту → EN → slug (D17). *Чому:* тег без новин у фільтрі веде в порожню стрічку, а сторінки з `noindex` у sitemap бути не повинні; тег із самими чернетками не з'являється на сайті раніше за новину. За кодами символів українські «Є», «І», «Ї» стали б перед «А», а «Ґ» — після «Я».
- ⭐ **`GET /tags/{slug}` віддає будь-який тег** — і без опублікованих новин: сторінка порожнього тегу існує (👤 б: `noindex`), 404 — лише для неіснуючого.
- ⭐ **Список адмінки** — усі теги за slug-ом, назви всіма мовами (порядок мов — `Language.sortOrder`) і `postCount`: новини будь-якого статусу, крім видалених (soft delete). *Чому:* видалення тегу прибере його й з чернеток — підтвердження має назвати справжню кількість. `POST` і `PUT` повертають ту саму форму — адмінка оновлює рядок списку без повторного запиту (👤 в).
- ⭐ **Видалення — одразу, фізично й каскадом** (`PostTag`, назви); підтвердження з кількістю новин — діалог в адмінці (M1.5), до того — Swagger. *Чому:* так видаляють теги Ghost і мітки GitHub — API видаляє, інтерфейс питає; «409 + повторний запит з підтвердженням» — другий крок в API, а UI однаково питає сам.
- ⭐ **`UNKNOWN_TAG` — у постах**, однією перевіркою з клубами й турнірами (`PostRepository.countExistingRelations`). Гонка «тег видалили між перевіркою і записом новини» → FK → повторна перевірка → та сама 400 `UNKNOWN_TAG`, а не 500 (`throwIfRelationVanished`; e2e — видалення тримає окрема транзакція). *Чому:* це перевірка зв'язків самої новини; винести лише теги — розірвати одне правило на два місця.
- ⭐ **Тег у новині й у списку — одна схема `TagDto`** (раніше `PostTagDto`, JSON той самий) і одна функція `toPublicTag` (`tags/tag-response.ts`). *Чому:* тег на сайті має однакову форму скрізь — і в картці новини, і у фільтрі.

## Як роблять сильні команди
- Фасетний пошук (Amazon, Booking): «або» всередині фасету — ще один тег розширює список, «і» між фасетами — звужує.
- WordPress (`get_terms`, `hide_empty`) за замовчуванням ховає теги без новин; Ghost і WordPress дають задати slug тегу при створенні.
- The Guardian, BBC: тег — сторінка теми з власною адресою (`/football/transfer-window`).

## Наслідки
- Таблиці — з v5 (D17). 👤 (після рев'ю) Міграція `0009_tag_constraints` — CHECK у БД (дубль `constraints.sql`): `Tag_slug_format_check` (формат `SLUG_PATTERN`, ≤ 50) і `TagTranslation_name_check` (не з самих пробілів, ≤ 50) — бо теги пише й сід з експорту, в обхід API. ⭐ Мінімум назви (2) — лише в API: `char_length` рахує символи, а JS — UTF-16, тож емодзі-назву, яку прийняло API, мінімум у БД відхилив би. Змінити межу назви чи формат slug-а — тепер і міграцією.
- Контракт: нові шляхи `/tags…` і схеми `TagDto`, `AdminTagDto`, `CreateTagDto`, `UpdateTagDto`, `DeletedTagDto`; `PostTagDto` → `TagDto` (JSON у стрічці й новині не змінився, web / admin цю назву не використовували). `GET /tags/{slug}` і `PUT` / `DELETE /tags/{id}` — як `/posts/{number}` і `/posts/{id}`.
- Обгортки типів (`packages/types/src/tags/`) — разом з першим користувачем у M1.5: пакет експортує лише те, чим користуються web / admin (M1.3.5).
- До M1.5 теги створюють і видаляють через Swagger. Заготовка тіла `POST /tags` у Swagger UI — без `slug` (інакше `"slug": "string"` став би адресою тегу назавжди).
- Помилку в slug-у виправляє лише новий тег: створити правильний → перепризначити новини → видалити старий. Злиття тегів і редирект зі старого slug-а — коли знадобиться ([`backlog.md`](../backlog.md), з M1.5.3.1 — [D51](D51-admin-tags.md)).
- Назви не унікальні (D17): двом тегам можна дати однакову українську назву; англійські дублі ловить slug.
- Публічний список — без пагінації й без кількості новин: тегів десятки; «популярні теги» — [`ideas.md`](../ideas.md).
- Видалення незворотне: помилковий id у Swagger прибере тег з усіх новин. Бекапи — [D32](D32-backups.md).

## Розглянуті альтернативи
- Суфікс при колізії (`transfers-2`) — відхилено: дубль теми замість помилки «такий тег уже є».
- Видалення тегу з новинами — 409 `TAG_IN_USE` і повтор з `?force=true` — відхилено: підтвердження однаково показує UI, а API-крок нічого не додає.
- У публічному списку — усі теги, і без новин — відхилено: порожні фільтри й сторінки з `noindex` у sitemap.
- Змінний slug (WordPress і Ghost дозволяють) — відхилено: адреса вже в посиланнях, редирект потребував би історії slug-ів.
- Перевірка `UNKNOWN_TAG` у модулі тегів (`TagService` для постів) — відхилено: клуби й турніри лишились би в постах, одне правило — у двох місцях.
- Кількість новин у публічному тегу — відхилено (YAGNI): споживача немає; сторінка тегу дізнається про порожність зі стрічки (`total`).

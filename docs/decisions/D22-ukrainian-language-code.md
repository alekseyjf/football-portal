# D22 — Код української мови: `uk` скрізь

- **Статус:** ✅ прийнято · 2026-10-08 · 👤 рішення власника (+ ⭐ редирект)
- **Етап:** M1.2
- **Уточнює:** [D8](v5-foundation.md) (мови з таблиці `Language`)

## Контекст
Зараз українська позначена `ua` в URL (`/ua/…`), у БД (`Language.code`), в API (`?lang=ua`) і в `messages/ua.json`. Але `ua` — це код **країни** (ISO 3166-1), а код **мови** — `uk` (ISO 639-1; Велика Британія як країна — `GB`, `.uk` — лише доменна зона). Через це сторінки віддають невалідний `<html lang="ua">`: Google ігнорує невалідні `hreflang`, скрінрідери не впізнають мову. Браузер шле в Accept-Language саме `uk`, тому в `proxy.ts` живе нормалізація `uk → ua`.

## Рішення
- 👤 Один код — `uk` — у всіх шарах: URL-сегмент `/uk/…`, `Language.code`, `?lang=uk`, `messages/uk.json`, `<html lang="uk">`, `hreflang="uk"`. Для `Intl` — `uk-UA`, для `og:locale` — `uk_UA`.
- ⭐ Тимчасовий редирект `/ua/*` → `/uk/*` (308) у `proxy.ts`: зміна URL без редиректу ламає закладки й посилання; прибрати перед продом.
- Чи нормальна це практика — так: стандарт BCP 47 / ISO 639-1; так роблять Wikipedia (`uk.wikipedia.org`), Google (`hl=uk`), більшість багатомовних сайтів. Сегмент `/uk/` іноді плутають з Великою Британією, але Google визначає мову за `hreflang`, а не за схожістю на назву країни.

## Наслідки
- Міграція даних `ua → uk` (первинний ключ `Language` + зовнішні ключі `PostTranslation`, `TagTranslation`) — саме міграцією, бо dev-БД стане БД тест-сервера ([D31](D31-test-environment.md)).
- Прибираємо `normalizeAcceptLanguageForAppLocales`; оновлюємо `packages/types`, `packages/validation`, адмінку, seed, документацію.
- Проду ще немає — зміна URL нічого не коштує для SEO.

## Розглянуті альтернативи
- `ua` в URL + `uk` у тегах — відхилено 👤: два коди для однієї мови = плутанина в коді й даних.
- `uk-UA` в URL — зайве: регіональних варіантів української не плануємо.
